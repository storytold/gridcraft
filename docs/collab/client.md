# Клиент совместного редактирования GridCraft

Крейт `crates/collab-client` (native-only) и интеграция в `crates/ui-egui` /
`apps/gridcraft`. Фича собирается Cargo-feature `collab`, по умолчанию **выключена**: без неё
в бинаре нет ни сети, ни изменений поведения.

## Включение

```bash
cargo run -p gridcraft --features collab -- book.xlsx
```

Окружение (все проверяются один раз при старте, одиночный режим без них не меняется):

| Переменная | Обязательна | Смысл |
|---|---|---|
| `GRIDCRAFT_COLLAB_URL` | да | `ws(s)://host/v1/sessions/<id>/ws` |
| `GRIDCRAFT_COLLAB_TOKEN` | да | подписанный токен кабинета (в URL и логи не попадает) |
| `GRIDCRAFT_COLLAB_NAME` | нет | имя в списке участников, по умолчанию `User` |

Соединение открывается в фоновом потоке со своим tokio runtime; UI показывает `Connecting…`,
пока не пришёл `welcome`. При обрыве — реконнект с backoff (0.5 с → 30 с), неподтверждённые
операции повторяются с теми же `opId` (дедуп на сервере).

## Что происходит с командой

Команда пользователя проходит через [`SheetApp::run_command`] и, если её класс разрешён
(`collab::classify`), отдаётся `Synced`:

- **merge** (`cell.*`, `range.*`, `home.*`, `data.*`, `formulas.*`, `review.*`, …) —
  применяется локально сразу (preview), отправляется операцией; на `applied` серверная дельта
  правит значения зависимых формул (volatile, Python, precision-as-displayed), на `rejected`
  preview откатывается `edit.undo`.
- **structural** (`home.insert`, `home.delete`, `sheet.move`, `sheet.rename`, `table.*`) — не
  применяется оптимистично: сервер решает, куда сдвинулись адреса. Приходит `applied` с
  нормализованной командой и новой картой листов (`sheetKey ↔ имя`), клиент применяет команду
  через `Session::apply_remote` и обновляет карту.
- **чужая merge-команда** — `apply_remote` (структура, формулы, стили) + `Session::apply_values`
  (авторитетные значения).
- **вне allowlist** (`file.*`, `view.*`, `print.*`, `python.*`, `macro.*`, `edit.undo`/`redo`) —
  остаётся локальной; undo/redo перехвачены отдельно (см. ниже).

## Undo

Сервер хранит по каждому участнику до 200 обратимых шагов (`CellSnap`: значение, формула,
стиль до/после). `edit.undo` уходит как `undo{opId}` — это **новая операция** с новой версией,
она не откатывает чужие правки:

- все ячейки шага должны всё ещё содержать то, что оставил шаг; иначе `rejected{code:"conflict",
  retryable:true}` и клиент ресинкается;
- отмена структурных правок в v1 не поддерживается (как и redo) — кнопка Redo возвращает
  сообщение «redo is not available in a shared session»;
- история живёт в комнате: реконнект её сохраняет, рестарт сервера — нет.

## Presence и роли

- Активный лист, ячейка, выделения отправляются 10 раз в секунду (`Presence`) и рисуются
  рамками цвета участника; список участников и состояние связи — в статус-баре.
- `viewer`: сервер отклоняет операции до движка, клиент не делает preview и не меняет книгу;
  статус-бар показывает `View only`.
- `owner`/`editor` — полный набор разрешённых команд.

## Reconnect и снапшот

`hello.lastVersion` меньше головы — сервер сам догоняет: хвост журнала или `snapshot` чанками
(768 КиБ base64) и `resynced`. Клиент заменяет документ снапшотом, сохраняет карту листов и
продолжает. Пока идёт догон, соединение не получает живых дельт, поэтому дельта не обгоняет
снапшот.

## Чего нет в v1

- **Redo** и отмена структурных правок.
- **Offline-очередь**: операции уходят только при живом соединении; после реконнекта
  повторяются неподтверждённые.
- **Commit из UI**: сохранение инициирует кабинет через `POST /v1/sessions/{id}/commit`
  (server-to-server, `INTEGRATION.md` §4.1); локальный `file.save` пишет локальную копию.
- **Web-клиент**: в WASM сеть не компилируется; браузер говорит тем же протоколом через
  host-сообщения (`INTEGRATION.md` §6), адаптер повторяет `Synced`.
- Несколько окон одного пользователя: один `actorId`, presence одного окна (открытый вопрос
  RFC §13.6).
