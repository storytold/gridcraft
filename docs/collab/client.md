# Клиент совместного редактирования GridCraft

Крейт `crates/collab-client` (native-only) и интеграция в `crates/ui-egui` /
`apps/gridcraft`. Фича собирается Cargo-feature `collab`, по умолчанию **выключена**: без неё
в бинаре нет ни сети, ни изменений поведения.

## Включение

```bash
cargo run -p gridcraft --features collab -- book.xlsx
```

Окружение (все проверяются один раз при старте, одиночный режим без них не меняется):

| Переменная | Обязательна | Смысл |
|---|---|---|
| `GRIDCRAFT_COLLAB_URL` | да | `ws(s)://host/v1/sessions/<id>/ws` |
| `GRIDCRAFT_COLLAB_TOKEN` | да | подписанный токен кабинета (в URL и логи не попадает) |
| `GRIDCRAFT_COLLAB_NAME` | нет | имя в списке участников, по умолчанию `User` |

Соединение открывается в фоновом потоке со своим tokio runtime; UI показывает `Connecting…`,
пока не пришёл `welcome`. При обрыве — реконнект с backoff (0.5 с → 30 с), неподтверждённые
операции повторяются с теми же `opId` (дедуп на сервере).

## Что происходит с командой

Команда пользователя проходит через [`SheetApp::run_command`] и, если её класс разрешён
(`collab::classify`), отдаётся `Synced`:

- **merge** (`cell.*`, `range.*`, `home.*`, `data.*`, `formulas.*`, `review.*`, …) —
  применяется локально сразу (preview), отправляется операцией; на `applied` серверная дельта
  правит значения зависимых формул (volatile, Python, precision-as-displayed), на `rejected`
  preview откатывается `edit.undo`.
- **structural** (`home.insert`, `home.delete`, `sheet.move`, `sheet.rename`, `table.*`) — не
  применяется оптимистично: сервер решает, куда сдвинулись адреса. Приходит `applied` с
  нормализованной командой и новой картой листов (`sheetKey ↔ имя`), клиент применяет команду
  через `Session::apply_remote` и обновляет карту.
- **чужая merge-команда** — `apply_remote` (структура, формулы, стили) + `Session::apply_values`
  (авторитетные значения).
- **вне allowlist** (`file.*`, `view.*`, `print.*`, `python.*`, `macro.*`, `edit.undo`/`redo`) —
  остаётся локальной; undo/redo перехвачены отдельно (см. ниже).

## Undo

Сервер хранит по каждому участнику до 200 обратимых шагов (`CellSnap`: значение, формула,
стиль до/после; для структурной правки — образ листов и состояние уровня книги до и после).
`edit.undo` уходит как `undo{opId}` — это **новая операция** с новой версией, она не
откатывает чужие правки:

- все ячейки шага должны всё ещё содержать то, что оставил шаг; иначе `rejected{code:"conflict",
  retryable:true}` и клиент ресинкается;
- `edit.redo` возвращает последний отменённый шаг, если ячейки всё ещё держат то, что оставила
  отмена; новая правка участника закрывает redo-ветку;
- отмена структурной правки (вставка/удаление строк или листов) — одна операция с образом
  границы: сервер присылает `applied.images` и `applied.book` (defined names, защита
  структуры, package/книжные `preserved` с chart sheets, VBA-проект, стили, `calc`), клиент
  заменяет листы и состояние книги через
  `Session::restore_structural`, `applied.sheets` обновляет ключи, `epoch` растёт; образ больше
  кадра едет частями `imagePart` (ADR-0013) — клиент собирает `{book, images}` и применяет
  только после `more:false`, а при обрыве последовательности не меняет документ и просит догон
  с версии до первой части; отмена возможна, только если после правки не было других
  операций, иначе `conflict`;
- история (undo и redo) живёт в комнате: реконнект её сохраняет, рестарт сервера — нет.

## Presence и роли

- Активный лист, ячейка, выделения отправляются 10 раз в секунду (`Presence`) и рисуются
  рамками цвета участника; список участников и состояние связи — в статус-баре.
- `viewer`: сервер отклоняет операции до движка, клиент не делает preview и не меняет книгу;
  статус-бар показывает `View only`.
- `owner`/`editor` — полный набор разрешённых команд.

## Reconnect и снапшот

`hello.lastVersion` меньше головы — сервер сам догоняет: хвост журнала или `snapshot` чанками
(768 КиБ base64) и `resynced`. Клиент заменяет документ снапшотом, сохраняет карту листов и
продолжает. Пока идёт догон, соединение не получает живых дельт, поэтому дельта не обгоняет
снапшот.

## Браузер и host-bridge

Страница кабинета открывает сессию сообщением `gridcraft:session`
(`sessionId`, `wsUrl`, JWT, роль; `INTEGRATION.md` §6). Токен уходит первым
кадром `hello`, не в URL и не в лог. Браузерная сборка (`crates/collab-web`)
ведёт ту же машину состояний `Synced`, что и десктоп, — меняется только
транспорт (`Link`: tokio/tungstenite или `web-sys::WebSocket`): preview,
авторитетная дельта, откат, карта листов, снапшот, per-user undo/redo общие.
Неподтверждённые операции переживают реконнект (те же `opId`), backoff тот же.

Статус и участники уходят в кабинет как `session-state` (по изменению) и
`presence` (10 Гц); `gridcraft:committed` возвращает version/etag. Save в
живой сессии — это `gridcraft:commit` без байтов: файл собирает и хранит
кабинет; Save As и экспорт остаются локальными.

`craft-web-host`/`craft-web-api` — из `copoka/craft-libs` rev
`7666e2b100d8cf12998f9b57d3b036964cc3189c` (ADR-0016 §3), пока
collaboration-сообщения не влиты в `storytold/craft-libs`. Без
`gridcraft:session` сетевых вызовов нет и сборка одиночная.

## Чего нет в v1

- Отмена структурных правок (redo merge-шагов есть).
- **Offline-очередь**: операции уходят только при живом соединении; после реконнекта
  повторяются неподтверждённые.
- **Commit из UI**: в браузере Save в живой сессии отправляет `gridcraft:commit`
  (кабинет владеет файлом); на десктопе сохранение по-прежнему инициирует кабинет
  через `POST /v1/sessions/{id}/commit` (`INTEGRATION.md` §4.1).
- ~~Несколько окон одного пользователя~~. Сделано (RFC §13.6): один `actorId` на
  пользователя, у каждого окна свой `windowId` (случайный, живёт всю сессию окна и
  переживает реконнект). Список участников и presence — по окнам, `undo`/`redo` — по
  `actorId`. На десктопе id делает `Client` (`Config.window_id`, в кадре — `windowId`),
  в браузере — страница кабинета (`clientId` из `gridcraft:session`-соединения);
  в host-списке строка на окно, `clientId` записи — это `windowId`.

## Проверка

```bash
cargo test -p gridcraft-collab-client     # 5 сценариев с двумя репликами и сервером
cargo test -p gridcraft-collab-web        # 5 тестов host-сообщений и двух web-реплик
cargo test -p gridcraft-web               # 11 тестов, включая host_session
cargo check -p gridcraft --features collab
cargo check -p gridcraft-web --target wasm32-unknown-unknown
trunk build                               # apps/gridcraft-web → dist/web
cargo test -p gridcraft-collab -p gridcraft-collab-server
```
