# Options: протокол совместного редактирования для GridCraft

> Артефакт Phase 0. Три варианта, различающиеся **механизмом** (что именно летит по
> проводу и что применяет сервер), а не настройками. Факты — из `study.md` (ссылки на
> файлы upstream). Кода фичи здесь нет.

- Проект: `gridcraft`, upstream `storytold/gridcraft` @ `6a8eb4ff`
- Дата: 2026-11-06, автор: `gridcraft/envoy`
- Критерии: `../.craft/protocol/AGENDA.md` §«Критерии оценки варианта»

## 0. Отправная точка GridCraft

| Факт | Следствие для протокола |
|---|---|
| Вся правка — `Session::execute(id, params: Json)`, реестр ~313–377 команд, у каждой документированная JSON-схема параметров | готовая единица операции уже есть; изобретать её не нужно |
| `Session.journal` (id+params, без паролей, 10k/64MB) и проигрывание списков команд (`automate.runScript`, `macro.run`) | журнал команд — рабочая модель, но лимиты не дают ему быть истиной сессии |
| Инверсий нет; undo = `Arc<Workbook>`-снапшоты (100 шагов / 128 MiB) | откат = состояние, а не обратная операция → per-user undo строится над дельтами |
| `CellStore::diff` и `Ctx.changed` дают точный список изменённых ячеек | дельта значений вычислима дёшево и уже используется внутри (footprint макросов) |
| Структурная правка (`insertRows`, `sheet.delete`…) переписывает формулы всей книги и сдвигает все объекты листа, затем полный пересчёт | структурные операции обязаны быть эксклюзивными и серверными |
| Volatile (`NOW`/`RAND`/`OFFSET`/`INDIRECT`) и Python-ячейки недетерминированы; `precision_as_displayed` меняет значения | «просто повторить команду у себя» расходится; нужен авторитетный результат |
| Часть параметров неявна (`range` = текущее выделение, `sheet` = активный лист); выделение живёт в окне, не в документе | сырые UI-команды нельзя слать как есть — нужен нормализованный конверт |
| XLSX с pass-through, `write_xlsx` из байтового среза, wasm-safe | commit на сервере возможен без GUI и без ФС кабинета |

## 1. Вариант A — команда как единица операции, сервер авторитетен

Клиент шлёт **нормализованную команду**: `{opId, baseVersion, cmd: "cell.set",
params: {...}, ctx: {doc, sheet, selection}}`, где параметры уже развёрнуты (никаких
«текущее выделение»). Сервер:

1. проверяет `role`/ACL и `baseVersion`;
2. выполняет команду в своей `Session` (`execute_headless`);
3. берёт `Ctx.changed`/`CellStore::diff` и шлёт всем **подтверждённую команду + дельту
   значений** `{sheet, cells: [{a1, value, formula?, style?}]}`;
4. пишет журнал сессии (свой, без лимитов клиентского) и периодически — снапшот
   (`serde_json` модели или `write_xlsx`).

Клиент применяет оптимистично у себя, при отказе сервера откатывается на дельту
`baseVersion` (у него есть COW-снапшот — `Arc<Workbook>`).

## 2. Вариант B — нормализованная операция над моделью (не команда)

Единица — **операция модели**: `SetCells`, `SetStyle`, `InsertRows`, `DeleteRows`,
`SetFormula`, `SetTable`, ... с адресами `(sheetUid, A1)`. Команда приложения только
транслируется в такие операции; сервер не вызывает `Session::execute`, а применяет
операции напрямую к `Workbook`, сам пересчитывает и рассылает операции (или дельты).
Структурные операции транслируют индексы (`OT`-подобно) для операций, пришедших после
них.

## 3. Вариант C — CRDT на хранилище ячеек

Пер-ячеечные LWW-регистры (ключ — стабильный ID ячейки, а не адрес), sequence-CRDT на
порядок листов/объектов; клиенты сходятся без сервера, сервер только хранит журнал и
снапшоты. Формулы, таблицы, pivot, CF, pass-through — либо LWW на структуру, либо
выносятся в «структурные» операции с отдельной блокировкой.

## 4. Сравнение по критериям AGENDA

| # | Критерий | A: команда + серверная дельта | B: нормализованные операции | C: CRDT по ячейкам |
|---|---|---|---|---|
| 1 | Не ломает round-trip XLSX | да: commit идёт через тот же `write_xlsx`, `Preserved` не трогается | да, если операции покрывают те же инварианты (`adjust`, `shift_sheet_features`) | да, если структурные части всё равно централизованы |
| 2 | 2–5 участников, 100+ листов | да: дельты, а не документ | да, дельты ещё мельче | да, но метаданные CRDT растут с числом ячеек |
| 3 | Не шлёт весь документ на нажатие | да, только команда + дельта ячеек | да, минимум | да |
| 4 | Корректный per-user undo | да: свой журнал дельт на пользователя, снапшоты сервера | да, но нужно писать инверсии для каждой операции | сложно: undo в CRDT — отдельная семантика |
| 5 | Headless-тесты (2–3 клиента) | да: `execute_headless` + CLI `run --script`, без GUI | да, но тестируется второй слой мутаций | да, но детерминизм сходимости проверять дорого |
| 6 | Реализуемо на Rust/WASM без тяжёлого CRDT | да: комната = `Session` + журнал, транспорт отдельно | да, но +второй путь мутаций в обход команд (дублирование `adjust`/`shift`/`check_arrays`) | нет: нужен зрелый CRDT-стек + переписывание модели |
| 7 | Один транспорт/конверт на 5 приложений | да: `{cmd|op, params, baseVersion}` подходит всем | частично: у каждого приложения своя модель операций | нет: у каждого приложения свои узлы |
| — | Совместимость с upstream house rules | высокая: ничего не меняет в модели, только точки вызова | средняя: новый публичный слой мутаций | низкая: меняет владение моделью |

Дополнительно для GridCraft:

- **Недетерминизм.** A решает его явно (дельта значений сервера), B — тоже (сервер
  пересчитывает), C — нет: два клиента получат разные `RAND()` и разойдутся.
- **Структурные правки.** Во всех вариантах эксклюзивны; в A это буквально «сервер
  выполнил `sheet.insertRows` и разослал результат», в B нужно вручную повторить
  `shift_sheet_features` + `rewrite`, в C — отдельный структурный канал поверх CRDT.
- **Pass-through.** A не касается `Preserved` вообще; B обязан повторять правила
  «ссылки в сохранённых частях не переписываются».
- **Объём кода.** A ≈ комната сессии + нормализация конверта + журнал. B ≈ A плюс второй
  слой мутаций и его тесты на паритет с командами. C ≈ A плюс CRDT и мост к формулам.

## 5. Рекомендация: A (команда как единица, авторитетная серверная дельта)

> **Канон букв (решение шины от 2026-11-06).** В общем протоколе буквы означают
> механизм, а не форму входа: **A** — клиент реплеит намерение локально, его результат
> считается истиной; **B** — сервер исполняет намерение и рассылает авторитетный
> результат; **C** — CRDT. В этой нотации рекомендация GridCraft — **B**: сервер
> исполняет нормализованную команду и возвращает дельту. Буква «A» ниже — локальная
> нумерация этого документа, оставлена для истории обсуждения; форма входа (`command` /
> `primitive` / `structural`) — подтип конверта, а не отдельный механизм.

**A выбрана потому, что GridCraft уже является command-first системой, а не потому, что
команды «привычнее».** Конкретно:

1. `Session::execute` — единственная точка мутации; у 300+ команд есть схемы параметров,
   `enabled`-проверки, защита от паники. Любой другой слой мутаций (B) обязан повторить
   `refresh_equations`, `check_protection`, `check_arrays`, `precision_as_displayed`,
   `auto_row_height`, `shift_sheet_features`, `rewrite` — это дублирование самой
   рискованной части `engine` (`crates/engine/src/cmd.rs:400-460`,
   `crates/engine/src/cmd/sheet.rs:125-260`).
2. Дельта для клиента не требует нового механизма: `CellStore::diff` уже используется для
   dry-run макросов, а `Ctx.changed` уже перечисляет изменённые ячейки.
3. Откат per-user undo ложится на существующие COW-снапшоты: сервер хранит состояниe на
   границе шага пользователя (`Arc<Workbook>` дешёв), инверсии не нужны.
4. Недетерминизм (`NOW`/`RAND`/Python/`precision_as_displayed`) закрывается тем, что
   **значения приходят с сервера**, а команда — только намерение.
5. Транспорт/конверт один для пяти приложений: `{opId, sessionId, baseVersion, kind:
   "command", cmd, params, ctx}` + обратный кадр `{opId, version, delta}`.

**Обязательные уточнения (иначе A развалится на таблицах):**

- **Нормализация конверта обязательна.** Сырые UI-команды зависят от выделения и
  активного листа; в шину уходит команда с явными `sheet` и `range`/адресами.
- **Структурные команды — эксклюзивная секция.** Пока сервер выполняет `Edit`-команду,
  обычные правки ячеек ставятся в очередь; клиенты не применяют структурную команду
  оптимистично, а ждут подтверждённой дельты (иначе их формулы и anchors разойдутся).
- **Снапшоты — моделью, commit — файлом.** Снапшот сессии: `serde_json` `Workbook`
  (+ версия, + uid листов); commit: `write_xlsx` на сервере. `CellUid` не вводим —
  идентичность ячеек остаётся адресной, а версии — серверные.
- **Журнал клиента не источник истины.** Лимиты 10 000/64 MB не годятся; сервер ведёт
  свой журнал сессии, клиентский остаётся для локального undo.

**Что берём из B:** нормализованный конверт (явные адреса, отдельный структурный тип
операции) и серверную дельту как подтверждение — это фактически «A с дисциплиной B».

**Что берём из C:** ничего для документа; только идею, что presence/курсоры — это
эфемерное состояние без истории (не журналируется, см. ADR по presence).

## 6. Что это означает для десяти измерений (позиция GridCraft)

| # | Измерение | Позиция GridCraft |
|---|---|---|
| 1 | Единица операции | нормализованная команда `(id, params, ctx)` + серверная дельта значений |
| 2 | Идентификаторы | `SheetUid` (рантайм) + `file_id`; ячейка — адрес + серверная версия; объекты — `id: u32` workbook-wide |
| 3 | Порядок и версии | серверный счётчик (`baseVersion`/`version`), идемпотентность по `opId`; Lamport не нужен |
| 4 | Конфликты | оптимистичное применение + откат на дельту; структурные команды сериализуются, не трансформируются |
| 5 | Снапшоты | снапшот `Workbook` (JSON) каждые N операций/минут + compaction журнала; commit через `write_xlsx` |
| 6 | Presence | отдельный эфемерный канал, без журнала, частота ≤ 10 Гц, selection + viewport |
| 7 | Топология сервера | один сервис, app-специфичный воркер/`Session` на сессию (модель и календарь пересчёта разные) |
| 8 | Auth/lease | JWT из кабинета, `role` проверяется сервером; viewer не получает права слать `op` |
| 9 | Commit | сервер собирает `.xlsx` (`write_xlsx`) и вызывает callback кабинета; 409 при изменении файла вне сессии |
| 10 | Offline и undo | undo per-user по серверным дельтам; offline — только очередь команд с серверной проверкой `baseVersion`, без автономной сходимости |

## 7. Риски и как их снимаем

| Риск | Митигация |
|---|---|
| Команда с неявными параметрами расходится у клиентов | нормализация в конверте + тест: одинаковые `params` дают одинаковую дельту |
| Структурная команда и правки ячеек в полёте | эксклюзивная секция, структурные команды не оптимистичны |
| Дорогой пересчёт (100k зависимых ~0.4 s, структурные — полный пересчёт) | дельта и throttling; структурные — редко и с индикатором; лимит размера команды |
| Клиент «залип» на чужой версии | сервер отвечает дельтой с версии клиента или просит полный снапшот |
| XLSX commit не проверен в Excel (`gaps.md` §1) | приёмка кабинета: commit → открыть в Excel; иначе фича не включается |
| Pass-through ссылки не пересчитываются | структурные правки только на сервере; в отчёте сессии — предупреждение |
| WASM: нет часов, один поток | тайминги/лимиты серверные, клиент только применяет дельту |
