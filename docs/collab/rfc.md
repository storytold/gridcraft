# RFC: совместное редактирование XLSX в GridCraft

- Статус: Draft (на ревью)
- Автор: `gridcraft/envoy`
- ADR: `bus/decisions/0001-op-unit.md` … `0010-undo-offline.md`,
  сводка — `.craft/protocol/ARCHITECTURE.md`
- Upstream issue/PR: не открыт (RFC сначала согласуется в шине)
- Факты: `upstream/docs/collab/study.md` (коммит `7ff301fa`), `options.md`

## 1. Контекст

GridCraft — command-first движок: вся правка идёт через `Session::execute(id, params)`
(`crates/engine/src/lib.rs:670`), у команд есть JSON-схемы, `enabled`-проверки и защита
от паники. Книга — COW-модель: `Workbook { sheets: Vec<Arc<Sheet>>, … }`, ячейки в полосах
по 64 строки за `Arc` (`crates/model/src/store.rs`), undo — снапшоты `Arc<Workbook>`
(100 шагов / 128 MiB), журнал команд ограничен 10 000 записей / 64 MB. Пересчёт —
граф зависимостей в `crates/calc`, при структурной правке — полный (`calc.recalc_all`),
при обычной — от dirty-множества (`calc.cells_changed`). Формат пишется `write_xlsx`
из байтового среза, непромоделированное сохраняется pass-through
(`crates/xlsx/src/passthrough.rs`).

Чего нет: сети в приложении (ни TCP, ни WS; web-сборка общается с кабинетом только
через `postMessage`), сессий, участников, per-user undo, стабильных ID ячеек и листов,
событий о правках. `TASK.md` требует совместную работу 2–5 человек на одной книге,
presence, согласованный пересчёт формул, per-user undo, commit `.xlsx` и сохранение
всех возможностей формата.

Этот RFC фиксирует, как десять ADR ложатся на GridCraft: что именно едет по проводу,
какие швы нужны в движке, как устроены сервер, клиент, тесты и поставка.

## 2. Цели и не-цели

**Цели.**

1. 2–5 участников правят одну книгу в реальном времени; у всех одинаковые значения и формулы.
2. Presence: активный лист, ячейка/диапазоны, viewport.
3. Per-user undo/redo, не откатывающий чужие правки.
4. Роли `owner`/`editor`/`viewer`, проверка на сервере.
5. Commit отдаёт `.xlsx`, который открывается в Excel без repair prompt; исходная версия сохраняется.
6. Одиночный режим — поведение по умолчанию; фича за флагом.

**Не-цели (v1).**

- автономная offline-правка и сходимость без сервера (ADR-0010);
- совместная работа с CSV/TSV (только `.xlsx`, см. `INTEGRATION.md`);
- несколько книг в одной сессии, аккаунты, облако;
- CRDT/OT: формулы, таблицы, pivot и pass-through не сводятся к per-cell CRDT (ADR-0004);
- паритет с Excel — отдельная дорожная карта.

## 3. Модель данных для синхронизации

### 3.1. Единица операции (ADR-0001)

Единица — **транзакция одного пользовательского действия**: нормализованное намерение
клиента + авторитетный результат сервера.

```json
{"opId":"<uuid>","doc":"<fileId>","baseVersion":41,"kind":"command|structural",
 "target":{"sheet":"<sheetKey>","a1":"B2:D9"},
 "payload":{"cmd":"cell.set","params":{"cell":"B2","input":"=SUM(A1:A9)"}},
 "preview":"<uuid клиента>"}
```

GridCraft использует два `kind`:

- `command` — команда реестра, у которой параметры **уже нормализованы**: `sheet` и
  `range`/адреса явные, `selection` не подразумевается. UI-вызов
  `home.bold` без диапазона на проводе превращается в `format.bold {range:"Sheet1!B2:D9"}`.
- `structural` — команды, меняющие структуру и адреса: `sheet.insertRows`,
  `sheet.deleteRows`, `sheet.insertCells`, `sheet.deleteCells`, `sheet.move`,
  `sheet.delete`, `sheet.rename`, `table.*` со сдвигом. Они эксклюзивны (ADR-0004).

Allowlist v1 (по группам `crates/engine/src/cmd/*`): `cell.*`, `range.*`, `edit.*`
(кроме undo/redo), `format.*`, `home.*` (форматирование), `data.*` без внешних
источников, `insert.comment`/`review.*`, `formulas.*` (кроме what-if), `table.*`,
`sheet.*` (structural), `pivot.refresh`, `chart.*` (без внешних данных).
Denylist v1: `file.*`, `app.*`, `ui.*`, `view.*`, `print.*`, `macro.*`, `automate.*`,
`python.*` (исполнение кода — только локально), `data.getData`/`fromTextCsv`,
`link.open`, `password`/протекция, `mcp`.
Denylist — свойство **сервера**, не клиента: команда вне allowlist получает
`rejected{code:"forbidden"}`.

Ответ сервера — авторитетная **дельта значений**:

```json
{"type":"applied","opId":"...","version":42,
 "result":{"command":{"id":"cell.set","params":{...}},
           "delta":{"sheet":"<sheetKey>",
                    "cells":[{"a1":"B2","value":"45","formula":"=SUM(A1:A9)","style":"<StyleId>"}],
                    "spill":{"C2:C9":["…"]},
                    "objects":{"deleted":[12],"created":[13]}}}}
```

Дельта обязательна: вычисленные значения — содержимое XLSX (`<v>`), а пересчёт
недетерминирован (`NOW`, `RAND`, `OFFSET`/`INDIRECT`, Python-ячейки,
`precision_as_displayed`). Клиент не выводит истину из своего исполнения.

### 3.2. Идентификаторы (ADR-0002)

| Сущность | Wire-адрес | Выдача и устойчивость |
|---|---|---|
| лист | `sheetKey` (UUID сессии) | сервер сопоставляет `SheetUid` (рантайм) ↔ `file_id` ↔ имя; карта живёт в снапшоте, в файл не пишется |
| ячейка | `(sheetKey, A1)` + `baseVersion` | ID нет; адрес валиден в пределах версии; после `structural` старые адреса отклоняются `retryable:false` |
| таблица/график/фигура/картинка/спарклайн/слайсер/control/pivot | `id: u32` + надгробие | `Workbook::next_object_id`/`free_object_ids`; в сессии id не переиспользуются |
| имя (defined name) | текст имени | переименование — операция с `from`/`to` |
| стиль | `StyleId` в составе ячейки/дельта | стиль интернирован; отдельного ID узла нет |

Надгробия живут не меньше окна дедупа журнала. Операция по удалённому листу/объекту →
`rejected{code:"stale", retryable:false, hint:{version}}`.

### 3.3. Документ на сервере (ADR-0005)

- **База**: JSON `Workbook` (`serde_json`) + **opaque-блоб `preserved`** и `source_dir`
  из исходного файла + карта ключей `{sheetKey, SheetUid, file_id, name}` + `version`.
  Без блоба JSON-снапшот теряет custom XML, внешние ссылки, connections, query tables,
  form/ActiveX, OLE, фон листа, printer settings (`preserved` помечен `#[serde(skip)]`).
- **Хвост**: журнал операций после базы (op, версия, actor, время), обрезается снапшотом.
- **Восстановление**: загрузить базу → `Calc::rebuild(&wb)` → применить хвост.
- **Commit** — отдельная операция: `write_xlsx(&wb)` из базы+хвоста, не из снапшота.

## 4. Протокол

### 4.1. Транспорт

WebSocket, WSS. Один фрейм — один JSON-объект. Лимиты: `op` ≤ 1 MiB, `applied` ≤ 8 MiB
(дельта больших `range.setValues` чанкуется по 64 KiB), `presence` ≤ 2 KiB,
`snapshot` — чанки по 1 MiB с `seq`. Сжатие permessage-deflate, если договорится
транспорт; бинарный формат в v1 не вводим.

### 4.2. Сообщения

| Тип | Направление | Поля | Семантика |
|---|---|---|---|
| `hello` | C→S | `v, app:"gridcraft", doc, jwt, client{name,ver}, lastVersion?` | auth + join; токен только здесь |
| `welcome` | S→C | `sessionId, actorId, role, lease, version, epoch, keys[], participants, capabilities` | старт; `keys` — карта `sheetKey ↔ имя` |
| `op` | C→S | `opId, doc, baseVersion, epoch, kind, target, payload, preview?` | операция |
| `applied` | S→C | `opId, version, epoch, result{command?,delta?}, actorId` | авторитетный результат |
| `rejected` | S→C | `opId, code, retryable, hint{version,epoch}, details?` | отказ |
| `presence` | C↔S | `sheetKey, active, ranges[], viewport, editing?` | эфемерно |
| `resync` | C→S | `from` | запрос базы/хвоста |
| `snapshot` | S→C | `mode, version, seq, bytes/chunk` | база и/или хвост |
| `commit` / `commit-result` | C↔S / S→C | `expectedVersion?` / `bytes, sha256, version, warnings[]` | сборка файла |
| `ping`/`pong` | C↔S | `nonce` | heartbeat и продление lease |
| `error` | S→C | `code, message, retryable` | фатальная ошибка соединения |

`code` ∈ `auth|lease|forbidden|invalid|stale|conflict|too-large|rate-limit|internal`.

### 4.3. Порядок и версии (ADR-0003)

- `version` — один монотонный счётчик на документ; присваивает сервер.
- `opId` — UUID клиента; дедуп **до исполнения**; окно (≥24 ч или ≥10 000 операций)
  персистентно и восстанавливается из журнала при рестарте, иначе повтор после
  падения исполнит операцию дважды.
- `baseVersion` — контекст, не блокировка; `structural` требует `baseVersion == head`.
- `epoch` — счётчик структурных правок документа. Растёт на каждой `structural`;
  операция со старым `epoch` получает `rejected{code:"stale", retryable:false}` и
  клиент делает `resync` (в PDF это отдельное поле ADR-0002; в GridCraft `epoch` —
  производное от журнала и служит быстрым признаком «адреса сдвинулись»).
- Presence и `ping` версию не меняют.

### 4.4. Конфликты (ADR-0004)

| Ситуация | Политика | Что видит пользователь |
|---|---|---|
| двое правят одну ячейку | обе применяются по порядку; побеждает последняя | своё значение заменяется дельтой сервера; тост «изменено другим» (опционально) |
| правка ячейки, от которой зависят формулы | сервер применяет и пересчитывает; дельта несёт значения зависимых | числа обновляются; формулы не переписываются |
| `insertRows` во время чужой правки ячеек | `structural` эксклюзивен: правки ячеек ждут | короткая блокировка UI «применяется структурная правка» |
| двое делают `structural` | очередь FIFO; второй ждёт `applied` | индикатор ожидания |
| правка в удалённый/сдвинутый адрес | `stale`, `retryable:false`; клиент ресинкается | «лист изменился, обновлено» |
| запись в spill другого пользователя | `check_arrays` → `invalid`, `retryable:false` | ошибка как в одиночном режиме: «нельзя изменить часть массива» |
| правка защищённой ячейки | `check_protection` → `forbidden` | как сейчас: защищённый лист |
| viewer шлёт `op` | `forbidden` до исполнения | UI не показывает редактор |
| переименование/удаление листа | `structural`; формулы по имени переписываются на сервере | имена листов и формулы обновляются у всех |

OT не используется: сервер применяет к head (ADR-0004). LWW для содержимого запрещён.

### 4.5. Reconnect и догон

1. Клиент присылает `lastVersion`; если он в хвосте — `applied`-операции с `lastVersion+1`.
2. Если версия вытеснена — `resync` → `snapshot{mode:"base+tail"}` чанками, затем
   непринятая очередь повторяется с теми же `opId`.
3. Оптимистичный preview сверяется с дельтой: при расхождении preview отбрасывается,
   применяется серверная дельта.
4. Таймаут реконнекта и backoff — на клиенте; сервер держит комнату TTL сессии.

### 4.6. Снапшоты и compaction (ADR-0005)

- Снапшот = база (JSON `Workbook` + блоб `preserved`/`source_dir` + карта ключей) +
  метаданные `{version, epoch, savedAt, sha256 исходника}`.
- Частота: каждые 500 операций или 5 минут, и обязательно при подключении нового
  участника, если хвост длиннее порога. Хранится 2 снапшота.
- Compaction: журнал обрезается по версии снапшота; окно дедупа хранится отдельно.
- Тест приёмки: «снапшот + хвост → commit» даёт `.xlsx`, у которого pass-through-части
  совпадают с исходными по sha256, а модель — с моделью после реплея.

## 5. Presence (ADR-0006)

```json
{"type":"presence","sheetKey":"…","active":"B2","ranges":["B2:D9","F1"],
 "viewport":{"topLeft":"A1","rows":40,"cols":12},"editing":false}
```

- Отдельный тип, не журналируется, `version` не меняет; ≤10 Гц, коалесцируется.
- Лимит 2 KiB, до 8 диапазонов (дальше `truncated:true`); `drop-stale` при backpressure.
- Выделение — состояние **окна**: клиент шлёт значения, сервер раздаёт участникам;
  несколько окон одной книги могут иметь разное выделение.
- TTL 30 с: без presence участник показывается «неактивен» и убирается.
- Цвет участника выдаёт сервер из `actorId` (стабильный в сессии).

## 6. Undo/redo на пользователя (ADR-0010)

- Сервер держит стек шагов **на актора**: шаг = COW-снапшот `Arc<Workbook>` на границе
  шага (клон — копия указателей полос) либо дельта `CellStore::diff`; реализация —
  деталь, поведение одинаковое.
- Undo — **новая операция** с `baseVersion = head`; рассылается как обычная дельта,
  видна всем. История клиентов не откатывается.
- Конфликт undo: если затронутые ячейки изменены после шага —
  `rejected{code:"undo-conflict", retryable:false, details:{cells:[…]}}`; молчаливой
  перезаписи нет.
- Redo симметричен; лимит на актора: 50 шагов или 32 MiB удержанного хранилища
  (меньше документного, т.к. акторов до 5), TTL — время сессии.
- История не пишется в файл и не уходит в кабинет.
- Offline: только повтор непринятых `command`-операций с `baseVersion`; `structural`
  offline запрещён (адреса разъедутся). Автономной сходимости нет.

## 7. Роли и права (ADR-0008)

- JWT в `hello`: `{iss, sub, aud, fileId, app:"gridcraft", role, sessionId, iat, exp}`;
  подпись асимметричная; токен не в URL и не в логах.
- Роль проверяется **на каждой операции**; `viewer` получает `forbidden` на `op`,
  но получает presence и снапшот.
- Дополнительно сервер проверяет защиту листа/книги (`check_protection`), а не UI.
- `owner` закрывает сессию (`session.close`), `editor` — нет.
- Автора комментариев/заметок подставляет сервер из `sub`, клиентский `author`
  не принимается.
- Lease: одна комната на файл; TTL и продление — heartbeat; потеря lease →
  `rejected{code:"lease", retryable:true}` и реконнект с новым JWT.

## 8. Commit и версии (ADR-0009)

- Собирает сервер: `write_xlsx(&workbook)` → `bytes`; ответ
  `{bytes, sha256, version, warnings[]}`.
- `warnings[]` — из `ReadReport::warnings` исходного чтения и из списка известных
  непромоделированных частей (`docs/gaps.md` §3); клиент/кабинет показывает список,
  а не булев флаг.
- `expectedVersion` (версия файла в кабинете) → `409`; сессия не перезаписывает,
  кабинет предлагает «сохранить копию».
- Триггеры: явное «Сохранить», выход последнего участника, TTL сессии (по умолчанию —
  явное + выход последнего).
- После commit сессия живёт, `dirty=false`, ключи не меняются; файл в сессию не
  перечитывается (иначе карта `sheetKey ↔ file_id` разъедется).
- Gate приёмки: committed `.xlsx` открывается в Excel/LibreOffice без repair prompt.

## 9. Сервер

- **Крейты**: `crates/collab` (конверт, типы, адаптер GridCraft: нормализация,
  allowlist, дельта) + `apps/gridcraft-collab-server` (бинарь: WS, JWT, lease,
  журнал, снапшоты, метрики).
- **Воркер**: один `Session` на документ в процессе; вход — `execute_headless`,
  выход — дельта из `Ctx.changed`/`CellStore::diff`; commit — `write_xlsx`.
- **Хранилище** (volume): `sessions/<fileId>/base.json`, `preserved.bin`,
  `keys.json`, `journal.jsonl`, `snapshots/<version>/`, `meta.json`. Файловый
  store в v1; Redis/Postgres — для lease и списка сессий кабинета.
- **Восстановление**: `meta` → база → `Calc::rebuild` → хвост журнала; снапшот
  каждые N операций; при отсутствии базы — `resync` невозможен, сессия закрывается
  с `error{code:"internal"}` и записью в метрику.
- **Лимиты**: документ ≤ 512 MB (как ридер), операция ≤ 1 MiB, дельта ≤ 8 MiB,
  участников ≤ 5 (v1), presence ≤ 10 Гц, сессий на процесс — по памяти.
- **Метрики**: активные сессии, участники, латентность `op→applied`, размер базы и
  хвоста, reconnect rate, отказы по кодам. **Логи без содержимого ячеек и токенов**
  (только `fileId`, `actorId`, версия, код).
- **Healthcheck**: `/healthz` (процесс + хранилище), `/readyz` (lease-хранилище).

## 10. Клиент

- **Feature flag**: Cargo-feature `collab` (по умолчанию **выключен**); при выключенном
  флаге ни сетевого кода, ни изменений поведения. Runtime-включение:
  native — `GRIDCRAFT_COLLAB_URL`; web — host-сообщение `<app>:session`
  (`INTEGRATION.md` §6) или `?collab=<wsUrl>` для отладки.
- **Нормализация команды**: перехват после `Session::execute` — берём `(id, params)`,
  подставляем явные `sheet`/`range` из `Selection`/`CommandInfo`, чистим запрещённое;
  при отказе сервера preview откатывается и применяется дельта.
- **Применение чужой операции**: новый путь в движке — `Session::apply_remote(...)`,
  который **не** пишет журнал и **не** пушит undo, но делает `refresh_equations`,
  `sync_headers`, `check_arrays`/`check_protection`-эквивалент на сервере уже выполнен,
  и пересчитывает (`cells_changed`). Это engine API, а не user-команда — house rule
  «everything is a command» касается пользовательских действий, не сетевого слоя.
- **UI**: оверлей выделений участников в `crates/ui-egui/src/grid/*`, список
  участников и индикатор синхронизации в статус-баре; viewer — `Session` в режиме
  только для чтения + отключённые команды.
- **Web**: `web-sys` WebSocket (сейчас в зависимостях нет; добавляется под
  `cfg(target_arch="wasm32")`), токен из host-сообщения; TCP control-канал в wasm
  не используется.
- **Комментарии/заметки**: автор из JWT; существующие команды `review.*` остаются.

## 11. Тесты

Headless-стенд: in-process сервер (комната + `Session`) и 2–3 клиентских `Session`
через `execute_headless`; GUI не нужен. Каждый сценарий — из `TASK.md` §8:

| # | Сценарий | Что проверяется |
|---|---|---|
| 1 | два клиента правят разные ячейки | обе дельты, одинаковые значения и `version` |
| 2 | конфликт одной ячейки | последняя побеждает, обе стороны видят одно значение |
| 3 | правка зависимой формулы | дельта несёт значения зависимых; `Calc` согласован |
| 4 | `insertRows` при активных правках | structural эксклюзивен, адреса не «съезжают» |
| 5 | `deleteRows` + запоздавшая правка | `stale`, клиент ресинкается, данные не воскресают |
| 6 | переименование листа | формулы переписаны, `sheetKey` стабилен |
| 7 | dynamic arrays/spill | `#SPILL!` и частичная запись запрещены как в одиночном режиме |
| 8 | reconnect и догон | `lastVersion` + хвост; при вытеснении — resync |
| 9 | viewer | `forbidden` на `op`, presence работает |
| 10 | per-user undo | отменяет только свои шаги; конфликт — частичный отказ |
| 11 | большая книга (10k+ строк, 3 листа) | латентность и отсутствие полной пересылки |
| 12 | commit | `.xlsx` открывается, pass-through сохранён (sha256), 409 при внешнем изменении |
| 13 | рестарт сервера | база + хвост восстанавливают `version` и модель |
| 14 | идемпотентность | повтор `opId` не меняет документ |

Дополнительно: `command_sequence_fuzz` с включённым collab-слоем (инварианты undo/redo
и round-trip), тест «снапшот + хвост → commit», замер `op→applied` на 100k зависимых
(цель — не хуже одиночного пересчёта + RTT).

## 12. Безопасность

- JWT только в `hello`; проверка `aud/exp/fileId/sessionId/role`; токен не в логах,
  снапшотах, URL и аудите.
- Origin/Referer проверяется при upgrade; соединение без `hello` за 10 с закрывается.
- `rejected` не содержит содержимого документа; ошибки — коды и позиции, не значения.
- Лимиты: документ, операция, дельта, присутствие, частота, число участников.
- Активный контент (VBA-макросы, Python, макросы GridCraft) не исполняется на сервере
  и не включается по сети: `Trust::FromFile` для сессии, `python.*`/`macro.*` в denylist.
- Клиент — недоверенный ввод: сервер валидирует `op` той же `enabled`/`check_*` логикой,
  что и одиночный режим.

## 13. Открытые вопросы

1. **Гранулярность дельты**: ячейки (как выше) или блоки `64×N`? Влияет на размер
   `applied` при `range.setValues` на 100k ячеек.
2. **Лимит команды**: `range.setValues` на большой диапазон может превысить 1 MiB —
   чанковать на клиенте (несколько `op` в одной транзакции) или поднять лимит?
3. **Очередь structural**: FIFO по документу или приоритет у `owner`? Влияет на UX
   при плотном потоке вставок строк.
4. **Стоимость снапшота**: JSON модели для книги 100 MB может быть дорогим; нужен ли
   инкрементальный снапшот по листам (`Arc<Sheet>` уже общий) в v1?
5. **Хост-контракт**: `<app>:session`/`presence`/`commit` в `INTEGRATION.md` §6 —
   поднимать ли contract version или добавить поля обратносовместимо?
6. **Несколько окон**: presence и undo при двух окнах одной книги — один `actorId`
   или разные? Предлагаю один актор на пользователя, окна различаются presence.
7. **CSV/TSV**: подтвердить, что collab только для `.xlsx` (в `INTEGRATION.md` так).

## 14. План поставки

Каждый шаг — отдельный PR, CI не трогаем (`AGENTS.md` house rules).

1. **Engine seams** (без сети): `Session::apply_remote`, публичный список изменённых
   ячеек после команды, снапшот/восстановление с `preserved`, тесты инвариантов.
2. **`crates/collab`**: конверт, allowlist, нормализация команд, дельта, тесты на
   двух `Session` без транспорта.
3. **`gridcraft-collab-server`**: WS, JWT, lease, журнал, снапшоты, метрики, healthcheck.
4. **Native-клиент**: feature flag, подключение, preview/откат, presence, viewer.
5. **Web-клиент**: WebSocket в wasm, host-сообщения, тот же протокол.
6. **Per-user undo/redo** и offline-очередь `command`.
7. **Перф и приёмка**: матрица §11, большой документ, commit → Excel.

PR 1–3 не меняют поведение при выключенном флаге; PR 4 включает фичу для нативной
сборки, PR 5 — для кабинета. RFC принят — начинаем с PR 1.
