# Large workbook performance

> **Last reviewed:** 2026-10-14 · **Last updated:** 2026-10-14 · **Change:** minor (reproducible large-workbook benchmarks and bounded navigation caches)

## Method

The native-only `crates/ui-egui/examples/large_workbooks.rs` benchmark generates deterministic
workbooks in memory. Production has no per-cell timing or allocator interception. Optional
`GRIDCRAFT_PROFILE=1` extends the existing commit/calc logging with filter preparation,
predicate evaluation and visibility-update timings. Keep it off for comparisons.

Build with `cargo build --release -p gridcraft-ui-egui --example large_workbooks` and run:

```powershell
./scripts/bench-large-workbooks.ps1 -Label current -Repeats 5
```

The wrapper runs datasets sequentially, records stdout/stderr, compiler, source commit,
hardware and process peak working set in `target/perf/<label>/`. Preserve the original
release executable before rebuilding; use **separate Cargo target directories for separate
source checkouts**, then compare it with the candidate on the same machine,
with no concurrent builds or benchmarks. A and H share values; both run 89% and 9%
selectivity numeric filters. Repetitions are warmed within one process and include the
first operation (cold caches); each dataset starts a new process.

| Dataset | Rows by default | Contents |
|---|---:|---|
| A | 100,000 | 12 numeric columns, no formulas |
| B | 100,000 | 9 numeric columns + 3 formulas per row (300,000 formulas) |
| C | 100,000 | Text, numbers, date formats; explicit variable height on every data row |
| D | 500,000 | 2 numeric columns |
| E | 1,000,000 | 2 numeric columns |
| F | 100,000 | 2 columns, stored only every 1,000 rows |
| G | 100,000 | Numeric input + cumulative formula dependency chain |
| H | 100,000 | A with both filter selectivities |

Row counts exclude one header. Synthetic workbooks are generated by GridCraft, never
Microsoft assets. The user's workbook is read from Downloads and is never written or
committed. Synthetic measurements do not substitute for its exact styles, functions or
sheets. The separate `workbook_file_perf` example measures file read/import, initial
graph/calculation, complete open, numeric filters on the largest sheet, CPU frames and
saving to memory. Reproduce with:

```powershell
cargo build --release -p gridcraft-ui-egui --example workbook_file_perf
./scripts/bench-large-workbooks.ps1 -Executable target/release/examples/workbook_file_perf.exe -Label real-current -InputWorkbook "$env:USERPROFILE/Downloads/Benchmark_GridCraft_vs_Excel_100k.xlsx" -Repeats 5
```

Input SHA-256: `18be34eeeb595391759bc9dd411af0aef0640fadbd43d4f96d5de6cea7854776`;
size: 7,627,635 bytes. The original-code comparison builds the same example in a detached
checkout of `d9d09f0`, preserving an independent executable. Complete open is measured
directly, including OS-cached file reads, import, dependency construction and initial calc;
it excludes desktop-window creation and the first displayed frame.

`scroll_cpu_frame` times `egui::Context::run_ui` including UI logic/layout/paint preparation
while moving through the sheet, at 1440×900 logical points, after five warmup frames.
It excludes tessellation, GPU submission, vsync and presentation. It is **not actual FPS**.
There are 100 frame samples and 50 geometry/range samples with five repetitions. Filter,
save, read and recalc have five samples; p95/p99 with that sample size are just maxima.
The quantile method is nearest rank. `xlsx_read_without_calc` includes package reading,
decompression, XML parsing, styles and formulas, but excludes initial calculation and UI.
`full_recalc` includes dependency-graph construction. Do not add percentiles to claim a
measured end-to-end open time. Working-set peaks cover the entire dataset lifecycle;
they include retained allocator capacity and repeated XLSX operations, not just live cells.

## Diagnosis

| Path | Cause | Baseline evidence |
|---|---|---|
| `model/store.rs::used_range`; both `ui-egui/grid.rs` scrollbars | Repeated full scan of stored rows to find column extrema, despite virtualized painting | A: two queries p50 13.307 ms; E: 48.445 ms |
| `ui-egui/grid.rs::Geo::new` | Rebuilds dimension prefix sums and outline groups whenever geometry is made | C: construction p50 1.512 ms, p95 3.245 ms |
| `engine/cmd/data.rs::apply_filter` | Formats values even for numeric/statistical/color criteria; clones values; parses numeric criteria per row | A: filter p50 164.294/179.696 ms |
| `engine/cmd/mod.rs::commit` → `calc/recalc.rs::recalc_all` | Visibility change rebuilds dependencies and evaluates every formula | B: 300,000 evaluations per filter; filter p50 1,247.114/1,196.645 ms; full recalc 1,040.218 ms |
| `engine/cf.rs::CfCache::look`; `ui-egui/grid.rs::show` | Every visible cell cloned complete range statistics; even cell-local rules populated those statistics | Real workbook: one `cellIs` rule on K2:K100001; CPU frame p95 453.604 ms before optimization |
| `xlsx/read.rs`, `package.rs`, `sheet_read.rs` | Whole-workbook import, not streaming; shared strings already use `Arc<str>` and styles are interned | B: read without calc p50 3,811.230 ms; no import optimization proven yet |

Cell storage already uses sparse row-major BTreeMaps in 64-row copy-on-write bands.
Calculation already has incremental dirty propagation, indexed range dependencies,
bounded evaluation, and shared formula expressions. The grid already paints viewport panes;
the diagnosed costs are outside that virtualization. No storage replacement, thread pool,
parallel recalc or permanent filter index is introduced.

## Navigation changes and invalidation

`CellStore` caches one optional rectangle in `OnceLock`, populated on first query.
Insertion/removal invalidates it; changing an existing cell's content/style keeps it valid.
Range removal and shifts use those same mutators. `get_mut` cannot change stored coordinates.
Cloning preserves an independent cache; serialization omits it and equality ignores it.
The memory overhead is constant per store, with no duplicated cells or growing key map.

`GeometryCache` retains one sheet's row/column indexes and outlines through shared pointers.
Its identity is a `Weak<Sheet>`: it retains no cell data and cannot mistake a recycled pointer
for its previous sheet. `Arc::make_mut` invalidates the weak identity even with one owner.
Filters, resizing, outline edits, defaults, switching sheets/documents and undo snapshots
therefore rebuild on demand. Zoom, scroll, freeze placement, RTL and viewport geometry are
read afresh. Its bound is one sheet's explicit row/column metadata, not one entry per frame.

## Filter and conditional-format changes

Filter comparisons parse numeric constants once; numeric, color and statistical predicates
do not format text unnecessarily. Value lists use a temporary ASCII-folded hash set,
preserving `eq_ignore_ascii_case` semantics (not Unicode case folding). Both raw and formatted
display values still match, and blanks remain separate. No permanent per-column index is kept.

Filter-only changes can re-evaluate all formulas with the existing dependency graph. This
does not skip volatile formulas, visibility-sensitive functions, dynamic spills or cycles.
Any changed cell uses the original rebuild; table header synchronization disables reuse
conservatively for workbooks with tables, because it can rewrite structured references.

Conditional-format `RuleStats` is borrowed, rather than cloning its complete sorted vector
and duplicate-count dictionary for every painted cell. Cell-local rules no longer build
irrelevant range statistics. There is no additional retained conditional-format cache.
The real workbook exposed this cost, which is absent in the numeric synthetic datasets.

An intermediate real-file candidate run (`real-no-stat-clones`) was **discarded**: sharing
the target directory between the original/current source checkouts allowed local-package
artifacts to be reused. Its numbers are not optimization results. Local release artifacts
were then cleaned and all GridCraft crates rebuilt from the current source; the preserved
original executable remains the baseline. Raw logs are kept as an audit trail.

### Checks

Targeted bounds, geometry, mixed-value predicate, unordered-number comparison,
visibility-recalc equivalence and conditional-format tests passed. The initial full CI
attempt failed on `field_reassign_with_default` in the new benchmark, which was fixed.
The final `cargo xtask ci` run passed all eight steps: fmt, clippy (`-D warnings`),
workspace tests, assets, layers, WASM, parity and keytips. Workspace tests: **1,607 passed,
0 failed, 1 ignored**. The ignored timing-sensitive
`recalc_with_range_formulas_scales_linearly` test was then run separately in release and
passed (1.60 s test execution, after compilation). Generated parity/keytip checks initially
failed; regeneration produced no normalized Git content diff, and direct `--check`
commands passed afterward. Their files were not edited by hand.

An existing WASM-only `dead_code` warning for `Modified::Unknown` remains; WASM compilation
passed. PowerShell redirection represents ordinary Cargo stderr as `NativeCommandError`
records and can report shell exit 1 even for a successful runner; the final CI log itself
reports all eight steps passed. The offscreen snapshot was also rerun directly, exiting 0.
It generated `target/perf/viewport.png` (2880×1800, original sales sample); visual inspection
found aligned grid/header/scrollbar geometry, preserved conditional-format data bars/icons,
and correctly positioned charts. This is visual QA, not a measured GPU frame-rate result.
Logs: `target/perf/ci-complete.log`, `target/perf/snapshot.log`.

No functional regression was found in these checks. The initial small opening slowdown
did not reproduce in the opposite-order pair, so no consistent opening regression or
improvement is established. Timing variability is reported rather than hidden.

GPU FPS, separate
text-layout timings, allocation counts, lock contention and post-close process RSS require
additional measurements; this benchmark does not claim them. G exercises a long chain,
not a representative complex multi-sheet production graph.
Exact per-frame processed/visible-cell counters, dependency-invalidation counts and a
decompression/XML/style phase breakdown are also not instrumented. Geometry construction,
filter preparation/predicates/visibility (opt-in profiling), full UI CPU frames and total
read/import are measured at their respective boundaries, not inferred as finer phases.

Suggested review summary: large-sheet scrolling repeatedly scanned full data and copied
conditional-format statistics for visible cells. Bounded cell/geometry caches and borrowed
statistics remove those costs, while prepared predicates and unchanged-graph reuse reduce
filter processing without skipping formulas. Keep initial XLSX import/full recalc, GPU FPS
and selective visibility-sensitive recalculation as follow-up work requiring separate proof.
The changes are prepared for review on `perf/large-workbooks`; publication is authorized
by the contributor. Raw logs and the user's workbook remain local.

The local `plan/` and the sibling `craftrules` checkout are absent; use committed architecture,
gap and parity documentation. Reusable finding for craftrules: virtualizing cell painting is
insufficient if scrollbar extent queries and geometry construction still scan all data.
